Your path

Rules for every tool

  • Use AI with your FirstLine account. Claude, Gemini, ChatGPT for Teachers or Codex, signed in as you at FirstLine. Never a personal account for anything about students or staff.

  • Keep it in the two places. Code in FirstLine’s GitHub; data in FirstLine’s databases. Not on your laptop, not only in a chat.

  • It looks like FirstLine. Navy #002F60, orange #E47727, Open Sans on screen. The rest is in the FirstLine branding guide.

  • FirstLine information stays behind a FirstLine sign-in. Share with “FirstLine Schools”, never “Anyone with the link”. Nothing about a student or staff member on a public page.

  • Student information goes only to the people who need it. A Sheet shared with the right staff is fine day to day. Trends over time or across schools belong on the back end.

  • It has an owner. One named person keeps it running. If you change roles, hand it over first.

Publish a page from Claude

Fastest. FirstLine staff signed in to Claude.

Example: A weekly homework page or a one-page explainer. Write the content in a Doc first, with nothing about an individual student in it.

  1. In Claude: "Turn this into a single mobile-friendly HTML page. FirstLine colors: navy #002F60, orange #E47727. Font: Open Sans." Paste your content.
  2. The page appears in the panel on the right. Use Preview to see it. Ask for changes in the chat; each one updates the same page.
  3. At the top of that panel click Share → Publish. Copy the link (claude.ai/artifact/…).
  4. Who can open it: people signed in to FirstLine’s Claude. Nobody without a Claude account can open it, even with the link, so it is not for families or students. Send the link to one colleague to check it opens for them.
  5. To update: keep working in the same chat, then Share → Publish again. The link stays the same.

An interactive checklist that remembers each person’s ticks

Example: A weekly team checklist that lives on paper today.

  1. Paste the checklist into Claude: "Make an interactive checklist page. Remember each viewer’s ticks in their own browser. FirstLine colors, Open Sans."
  2. In Preview: tick three boxes, reload, and confirm they stayed ticked.
  3. Share → Publish. Copy the link and write down who can open it once you have tested.

Ask questions of FirstLine’s data: the BQ Project

Ask in plain English; see only your own students.

Example: "Which of my students missed more than three days this month?" answered from the real attendance data.

  1. In claude.ai, open Projects, then the Organization tab, and choose BigQuery Student Data. It is shared with all of FirstLine, so nobody has to add you.
  2. In the Project, when it asks you to connect BigQuery, sign in with your own FirstLine Google account. The connection knows who you are, and the data only returns the students you are allowed to see: your school, or several schools if you lead more than one.
  3. If it asks which project ID to use, the answer is fls-teacher-data.
  4. Ask in plain English. Never paste student data into the chat; the connection is the only door.
  5. An empty answer usually means "not one of your students", not missing data.

Pull FirstLine data into a Sheet, then publish it

A school’s live tracker, refreshed by a person through Claude.

Example: A real FirstLine tool: one school’s 3rd and 4th grade mastery tracker. Data comes from the BQ Project and a few other sources into a Sheet, with Claude helping automate the pull. An Apps Script web app turns the Sheet into a page with tabs, filters and a support status for each student.

  1. Pull the data you need through the BQ Project into a Sheet, with Claude doing the work.
  2. Publish the Sheet as a page with an Apps Script web app: the Google page, "A Sheet as a live web page".

Families. Anyone with the link.

A Sheet as a live web page

The page shows the current Sheet every time it opens.

Example: A duty schedule or club roster your team keeps in a Sheet becomes a page. It is the same route the school mastery tracker uses, with data pulled from the BQ Project.

  1. In the Sheet: Extensions → Apps Script. In Code.gs:
    Code.gs
    function doGet() {
  const sheet = SpreadsheetApp.getActive().getSheetByName('Schedule');
  const rows = sheet.getDataRange().getDisplayValues();   // strings, as shown in the Sheet
  const t = HtmlService.createTemplateFromFile('Index');
  t.header = rows[0];
  t.rows = rows.slice(1);
  return t.evaluate().setTitle('Schedule')
    .addMetaTag('viewport', 'width=device-width, initial-scale=1');
}
  2. File → New → HTML, name it Index. Ask Claude for a mobile-friendly table in FirstLine colors that uses these lines:
    Index.html
    <table>
  <tr><? for (const h of header) { ?><th><?= h ?></th><? } ?></tr>
  <? for (const r of rows) { ?>
    <tr><? for (const c of r) { ?><td><?= c ?></td><? } ?></tr>
  <? } ?>
</table>
  3. Deploy → New deployment → Web app. Then decide Execute as, which decides who sees what:
  4. Execute as: Me. The page reads the Sheet as you, so viewers don’t need access to the Sheet, and every viewer sees the whole tab. Fine for a duty schedule. Not for anything about a student or a staff member unless Who has access is narrowed to match.
  5. Execute as: User accessing the web app. The page reads the Sheet as the viewer. Share the Sheet only with the people who should see it, and everyone else is refused. Use this for anything about students. Each viewer approves the script once, on their first visit.
  6. Who has access: Anyone within FirstLine Schools, or Anyone only if the tab holds nothing personal. Copy the /exec URL, change a cell, reload: the change shows.
  7. Code changes later: Manage deployments → pencil → New version → Deploy.

Charts from a Sheet: Looker Studio

Charts, filters, scheduled refresh.

Example: The same Sheet as a report with a chart and a filter.

  1. lookerstudio.google.com → Create → Report.
  2. Add data → Google Sheets → pick the spreadsheet and the tab. Tick Use first row as headers. Add.
  3. Add a chart → Table. Set Dimension and Metric from the field list. One chart that answers one question.
  4. Share → Manage access. Link settings: Restricted, then Anyone at FirstLine Schools with the link can view. For named people, add their addresses.
  5. Freshness: Resource → Manage added data sources → Edit → Data freshness. Sheets sources refresh every 15 minutes to 12 hours.
  6. Viewers see whatever the source Sheet contains. Looker Studio does not filter by who is looking, so if people should see different slices, this is not the tool.
  7. Write the definition of each number under its chart in a text box. That stops the "why is your number different" conversation.

A PD survey that sends each presenter their own results

A form that runs itself every week.

Example: After each PD session, staff answer five questions on a phone. Every Friday at 3, each presenter gets an email with their own average rating and comments from the week, and nobody else’s. It runs in test mode, sending everything to you, for a week first.

  1. Write it down first, in a Doc: the questions; whether answers are anonymous or named; who sees the Sheet (the PD lead, not the presenters); and a list of things it must never do: "never sends one presenter’s comments to another", "never sends outside @firstlineschools.org".
  2. At forms.google.com → Blank form, add five questions with these exact titles: Session (Dropdown), Presenter (Dropdown), How useful was this session? (Linear scale, 1 to 5), One thing you will use (Paragraph), What would make it better? (Paragraph). Make the first three required.
  3. Anonymous or named: Settings → Responses. Turn on Restrict to users in FirstLine Schools and its trusted organizations either way. For anonymous, set Collect email addresses to Do not collect: people still sign in, but their address isn’t recorded. For named, choose Verified. Say which at the top of the form, because people answer differently.
  4. Responses → Link to Sheets → Create a new spreadsheet. Leave the Form Responses 1 tab alone.
  5. In the Sheet, add a tab named Presenters: column A each presenter’s name exactly as it appears in the Presenter dropdown, column B their FirstLine email. Row 1 is headers.
  6. Extensions → Apps Script. Replace Code.gs with this and Save. If you changed a question title, change it in the Q list at the top.
    Code.gs
    // PD survey: every Friday, each presenter gets their own results from the past week.
// The question titles below must match the Form exactly. Change them here if yours differ.
const TEST_MODE = true;                         // flip to false only after a week of clean test sends
const TEST_TO   = Session.getEffectiveUser().getEmail();
const Q = {
  session:   'Session',
  presenter: 'Presenter',
  rating:    'How useful was this session?',
  use:       'One thing you will use',
  better:    'What would make it better?',
};

function weeklyPresenterResults() {
  const book = SpreadsheetApp.getActive();
  const all = book.getSheetByName('Form Responses 1').getDataRange().getValues();
  const col = {};
  Object.keys(Q).forEach(k => { col[k] = all[0].indexOf(Q[k]); });

  // Presenters tab: column A the name exactly as in the Form's dropdown, column B their email.
  const emails = {};
  book.getSheetByName('Presenters').getDataRange().getValues().slice(1)
    .forEach(r => { if (r[0]) emails[r[0]] = r[1]; });

  const since = new Date(Date.now() - 7 * 864e5);
  const byPresenter = {};
  all.slice(1).filter(r => new Date(r[0]) > since).forEach(r => {
    const p = r[col.presenter];
    (byPresenter[p] = byPresenter[p] || []).push(r);
  });

  Object.keys(byPresenter).forEach(p => {
    const rows = byPresenter[p];
    const to = TEST_MODE ? TEST_TO : emails[p];
    if (!to) { console.log('no email on the Presenters tab for', p); return; }
    const avg = rows.reduce((s, r) => s + Number(r[col.rating] || 0), 0) / rows.length;
    const sessions = [...new Set(rows.map(r => r[col.session]))].join(', ');
    const list = c => rows.map(r => r[c]).filter(t => t !== '').map(t => '<li>' + esc(t) + '</li>').join('') || '<li>None</li>';
    MailApp.sendEmail({
      to,
      subject: (TEST_MODE ? '[TEST for ' + p + '] ' : '') +
               'Your PD feedback this week: ' + avg.toFixed(1) + ' / 5 from ' + rows.length + (rows.length === 1 ? ' person' : ' people'),
      htmlBody: '<p>Sessions: ' + esc(sessions) + '</p>' +
                '<p><b>One thing people will use</b></p><ul>' + list(col.use) + '</ul>' +
                '<p><b>What would make it better</b></p><ul>' + list(col.better) + '</ul>',
    });
    console.log('sent', p, rows.length);                 // shows in Executions
  });
}

function esc(t) {
  return String(t).replace(/&/g, '&amp;').replace(/</g, '&lt;').replace(/>/g, '&gt;');
}
  7. Pick weeklyPresenterResults from the function list and click Run. Approve the permissions with your FirstLine account. In test mode, every presenter’s email comes to you, marked [TEST for Name], so you can read exactly what each would get.
  8. Triggers (clock icon, left rail) → Add Trigger: function weeklyPresenterResults, Time-driven → Week timer → Every Friday → 3pm to 4pm. Save.
  9. Each Friday, open Executions (left rail). Every run is a row with its status and log lines, including any presenter missing from the Presenters tab.
  10. After a week of clean test emails, set TEST_MODE = false and save. Triggers pick up saved code at once; there is nothing to redeploy.
  11. Off switch: Triggers → the trigger’s menu → Delete trigger. A trigger runs under the account that created it and stops without telling anyone when that person leaves. Hand it over before you go.
  12. Presenters never get the Sheet itself. A Sheet has no per-person view, so the email is how each one sees only their own results.
  13. To see which sessions land across the whole year, or compare schools, put a chart on it with Looker Studio. Comparing year over year is the point where it belongs on the dedicated back end.

A Sheet has no per-person view. Anyone who can open it sees every row and every tab; protected ranges stop editing, not viewing. If a principal should see only their school, make one Sheet per school, or use Execute as: User accessing the web app with each school’s Sheet shared to that school.

When you’ve outgrown Google

Any one of these means it’s time for the dedicated back end:

  • Different people need to see different rows of the same data, and one Sheet per group has stopped being manageable.

  • You want trends over time or comparisons across schools, and the tabs keep changing shape as people add columns.

  • It has to refresh FirstLine’s data by itself. A Sheet can hold data a person pulls through the BQ Project, but it can’t fetch it from FirstLine’s data warehouse on a schedule.

  • Each entry gets reviewed or signed off, and you need to know who changed what and when.

  • The script keeps hitting Google’s limits on run time or emails per day.

Publish a page with GitHub Pages

Public: anyone with the address, even from a private repository. A real HTML page.

Example: The homework page again, as one HTML file Claude made for you (index.html).

Keeping code in GitHub, the FirstLine way

  • In the firstline-schools organization, not a personal account, so it survives you changing roles.

  • Private unless the content is meant to be public. A private repository is still readable by every member of the organization, and its history is permanent.

  • Never in a repository: passwords, keys or tokens, and no student or staff names, IDs or records, including "test data" typed from memory. Three of twelve invented student names in one prototype turned out to be real students.

  • A CLAUDE.md at the top: what the tool is and isn’t, how it goes live, who can see what. Claude reads it at the start of every session.

Build with datathe FirstLine starter kit

Many ways to build. Two places everything is kept.

Code lives in GitHub. Every tool’s code, with every change recorded, in FirstLine’s organization.
Data lives in FirstLine’s databases. BigQuery, and Firestore being tested. FirstLine’s own data, plus whatever your tool keeps.

Why data first

Google Cloud’s AI starter kit for lean teams lays out four steps, and puts data second: “AI agents built without business data are just a stepping stone.” FirstLine has already built the hard part.

  1. A first win. A form, a page, a checklist in Google or Claude.
  2. A data foundation. FirstLine’s warehouse in BigQuery, with each person’s access already scoped. Built.
  3. Prove value on that data. A real tool on the starter kit that reads it, and keeps its own.
  4. Scale. Automation and agents, once the tools above are working.

A real web app behind FirstLine sign-in that reads FirstLine’s data straight from BigQuery and keeps its own data in its own database, with each person seeing only what their role allows. Start a tool

Once per tool. You fill in one form; your tool arrives ready to build.

Example: A form staff fill in on a phone, where each school’s leaders see only their own school’s entries, and a monthly count for the network.

  1. You: make a free GitHub account at github.com/signup with your FirstLine email, and turn on two-factor authentication when it asks. Once, ever.
  2. You: write down, in a Doc, what the tool does, who uses it, and what each person may see. Ask the person who does the work how they do it today before you decide who the tool is for.
  3. You: fill in the FirstLine GitHub requests form. Choose Set up a back-end tool, and give your GitHub username, a short name for the tool (lowercase with hyphens, like pd-survey), who uses it, and which FirstLine data it needs.
  4. FirstLine’s GitHub admins: add you to FirstLine’s GitHub, make your tool from the starter kit, and connect it to Google Cloud with the data you asked for.
  5. You: get two emails. One is a GitHub invitation: click Accept. The other gives your tool’s name and web address. Your tool already works: open the address and you see a blank FirstLine page that already knows who you are.
  6. You: open claude.ai/code, choose your tool from the list, paste your Doc and say: "Here is what I want this tool to do. Ask me questions until you understand it, then write it up as the plan. Don’t build anything yet." Claude writes the plan into your tool; read it, and correct anything it got wrong.
  7. From here on, every change is the six moves in Make one change.

Keep your own data

Your tool’s own database, instead of a Sheet in someone’s Drive.

Example: A PD survey tool keeps every response; a walkthrough tool keeps each leader’s notes. Because it lives in BigQuery next to FirstLine’s data, you can compare it over time and across schools, and line it up with rosters or scores.

  1. Tell Claude what to keep, in plain words: "Each response should keep the session, the presenter, a 1 to 5 rating, and two comments." Claude adds it to your tool’s list of tables. Merge the change as usual.
  2. Open your tool and press Create tables. The tool creates them itself, in its own dataset in FirstLine’s tools project. Nobody else has to do anything.
  3. Every row records who added it and when, automatically. Nothing is ever deleted; a wrong entry is marked void with a reason.
  4. Adding a column later is a new change: tell Claude, merge, press Create tables again.
  5. Today a tool’s own data lives in BigQuery, built for comparing over time. Firestore, a database built for records people edit all day, is being tested as a second option. See Where data lives.

Make one change

The same six moves, every time.

  1. At claude.ai/code, under the box where you type, choose your repository. Leave the branch on main.
  2. Type what you want and press Enter. One change per request.
  3. Claude reads the repository (starting with CLAUDE.md), writes the code and its tests, and commits to a new branch. You watch it work.
  4. When it finishes you see a line like +42 -18. Click it and read what changed, file by file. You are the reviewer; if something is wrong, say so in the same conversation.
  5. Click Create PR and open it as a full pull request.
  6. On GitHub, wait for the green tick, then Merge pull request. About two minutes later the change is live. Open the tool and use it.
  7. Keep the branch current. Claude’s branch is copied from main when the conversation starts and doesn’t move. If anything has merged since, start your next request with: "Merge the latest main into this branch before you start, and tell me anything that conflicts."

When you get stuck

Everything here you do yourself, in the browser.

  1. The tool says its tables are missing: open the tool and press Create tables.
  2. You need a real job title or school name: press the lookup buttons on the tool’s setup page and copy the result into your chat.
  3. The tool says it needs a permission it can’t give itself: press Copy the request and send it to the person the tool names.
  4. The check is red on your pull request: click Details, copy the red lines into your chat and ask for a fix. A red test means the change broke something the tool promised: fix the code, not the test.
  5. The deploy is red after a merge: Actions tab → the red run → the failed step → copy the red lines into your chat. The previous version keeps running while you fix it.
  6. Claude tells you to run a command: tell it you have no terminal and ask for another way.
  7. Four things need an administrator, and the tool names them when it hits one: a password or API key; FirstLine data the tool wasn’t set up to read; making it reachable without a FirstLine sign-in; changing a Cloud Run setting.

Move an Apps Script tool to code

For a tool that works and has outgrown its Sheet.

Example: The school mastery tracker: data pulled through the BQ Project into a Sheet, published with Apps Script. As code, it reads FirstLine’s data directly with nobody pulling it, each school sees only its own students, and every change is recorded.

  1. Keep the Apps Script version running. People keep using it until the new one matches it.
  2. Start a tool from the starter kit (Start a tool). In the setup request, list everything the Sheet is built from: which FirstLine data (rosters, assessments, attendance) and anything outside the warehouse. The FirstLine data becomes a direct read; the reply says how the rest gets in.
  3. Put the Apps Script code in the repository so Claude can read the rules instead of guessing them. In the script editor, open each file (Code.gs, Index.html and the rest), copy it, and on GitHub use Add file → Create new file to save it under apps-script/ with the same name.
  4. Write down what the page already does: a screenshot of every tab, each filter, each status and the exact rule that sets it (for example: 75–100% strong, 65–74% approaching, 50–64% partial, 0–49% significant gap), and who may see it (staff at that school).
  5. First request in claude.ai/code: "Read the plan and everything in apps-script/. Don’t write code yet. Tell me how you would build this, which data you would read, and every rule you can’t find in either." Answer its questions; it adds your answers to the plan.
  6. Build one tab at a time, starting with the Overview, one change per pull request.
  7. Check the numbers against the old page. Pick ten students and compare them side by side. Every difference is either a bug or a rule the plan missed; fix the plan or the code, then check again.
  8. When they match, send people the new address. Then retire the old page: in the script editor, Deploy → Manage deployments → select it → Archive.

A tool students use

Approval first. This is the only route.

Example: A multiplication game that remembers which facts each student has mastered, picks up where they left off, and shows the teacher who needs help. Not a Claude page (students have no Claude accounts), not a Sheet in your Drive, not an outside service.

  1. Write five decisions in a Doc: what it is for; what it remembers; what it never collects (name, photo, free text about a child); how it knows which student it is (their FirstLine school account, or an anonymous code the teacher holds); who sees what; when data is deleted.
  2. Take the Doc to your supervisor and the academic lead for the subject. The answer is yes, no, or a smaller yes.
  3. Start the tool as above, saying in the setup request that students will use it.
  4. Build the smallest playable version first, one change at a time.
  5. Pilot with one class, teacher in the room. Check it against the plan, and ask a second AI to attack it against that list. Save what it finds.
  6. Sign-off before any other class uses it (see Before people use it).

What you get

A small web app on Google Cloud Run, in FirstLine’s project for builder tools. FirstLine sign-in sits in front of it, so nobody without a FirstLine account reaches it. It looks people up by job title and school in the staff roster, reads only the FirstLine data it was set up for, and keeps its own records (see Where data lives). Every merge deploys it in about two minutes and checks that it answers. Every morning a health check confirms it’s up.

A Claude artifact

Who can open it: people you invite, or anyone at FirstLine, signed in to FirstLine’s Claude. A link for people outside FirstLine works only if FirstLine’s Claude Owner turns that on. Before people use itthe checklist and sign-off

A short check before anyone other than you relies on the tool. Go down the list for what your tool does; skip what doesn’t apply.

Safe to Ship, from AI for Equity

FirstLine’s sign-off follows AI for Equity’s Safe to Ship model, in two halves, each with its own guide from AI for Equity. They are separate from this page, the FirstLine Builders Guide: this page helps you choose and build; Safe to Ship is how a tool is checked before people rely on it. The builder works AI for Equity’s Safe to Ship Builder’s Guide and keeps the evidence while building: the plan, the list of things it must never do, each check with what you saw, and a second AI’s attempt to break the access rules. The supervisor reviews it before launch and decides Ship, Ship with conditions or Not yet. Any No or Unsure rules out Ship.

  • Safe to Ship Builder’s Guide (AI for Equity) for the builder: what to do, and what to keep, at each step of the build
  • Safe to Ship Supervisor’s Guide (AI for Equity) for the supervisor: the pre-launch review, also usable as an AI skill
  • AI for Equity resources their video library
  • AI for Equity skills on GitHub

Use it for anything that runs on its own, keeps records, or that students use. A page or a shared Sheet needs only the checks below.

Every tool

  • Every date, time and policy on it has a source you can point to.
  • A second person can edit it.
  • The owner’s name and what it is for are written on it: the Sheet’s first tab, the site’s footer, the repository’s README.
  • Public pages: no student names, photos or individual information.

Sign-off: send the link to your supervisor.

Only some people may see it

  • The sharing setting is written down on the tool.
  • An account that should be refused was refused, and someone other than you tested it.
  • Apps Script: Execute as and Who has access are written down, with the reason.

Sign-off: your supervisor sees the link and the sharing setting.

It shows data that changes

  • It reads from the real source: no downloaded file, no pasted copy.
  • Every number’s definition matches the data team’s, and is written on the page.
  • Someone with less access opened it and saw only their slice, or everyone may see all of it.
  • How often it refreshes is written down.

Sign-off: your supervisor, plus the data team when the numbers are about students.

It runs on its own, or keeps records

  • What it does, and what it must never do, were written down before the build.
  • Every run shows up in a log you have looked at.
  • There is a one-step off switch, and you know where it is.
  • Everything it sends went to a test address first, for a week.
  • Every entry records who and when, and a wrong entry can be corrected.

Sign-off: your supervisor works the Safe to Ship Supervisor’s Guide (AI for Equity): Ship, Ship with conditions, or Not yet.

Students use it

  • Approved before the first student uses it.
  • Students are identified by school account or an anonymous code. No names stored.
  • Only the minimum data, in a FirstLine system.
  • You tried to see another teacher’s students and were refused.
  • When data is deleted is written down, and it happens.

Sign-off: your supervisor and the academic lead, using the Safe to Ship Supervisor’s Guide (AI for Equity). No student use on a Not yet.

Where data livesSheets, BigQuery, Firestore, Cloud SQL

Every tool keeps its information somewhere. Knowing which one, and what it is good and bad at, is most of choosing a path.

Google Sheets

In use everywhere

The database most people at FirstLine already use. Forms write into it; Apps Script and Looker Studio read from it.

Good for
A team-sized record: responses, a tracker, a schedule.
Watch for
Anyone who can open it sees every row. Columns drift as people edit. No record of who changed a cell beyond version history.

BigQuery: FirstLine’s data warehouse

In use

Where FirstLine’s own data lives: rosters, attendance, grades, assessments, staff. Source systems load it; nobody else writes to it. Its Google Cloud project is fls-data-warehouse.

How you reach it
Through the BQ Project in Claude (only your own students, through views in fls-teacher-data), or from a back-end tool that was set up to read specific parts of it. Never by copying it somewhere else.
Good for
Analysis: trends over time, comparisons across schools and years.

BigQuery: a tool’s own dataset

In use: the starter kit today

Each back-end tool gets its own dataset in the firstline-tools project and writes only there. The Health Office tool keeps its reports in firstline-tools.health_office.

Good for
Records you will analyze later; a full history of every change.
Watch for
It is built for analysis, not for records people edit all day. Edits are careful SQL, a column named after a reserved word (at) breaks every save, and rows saved with the fast method can’t be edited for about half an hour.

Firestore

Being tested

Google’s database for live app records: a form submitted, then corrected five minutes later.

Good for
Fast reads and edits of individual records. Costs close to nothing when nobody is using the tool.
Watch for
Not built for reports across many records, so records are copied to BigQuery for trends. Not yet part of the starter kit.

Cloud SQL (Postgres)

Being considered

A traditional database of related tables, for apps that need fast answers across many of them.

Good for
Performance apps: dashboards that slice large data quickly.
Watch for
It runs all the time, so it has a monthly cost even when nobody is using it. Not yet part of the starter kit.

A Claude page’s storage

Available

A page published from Claude can remember what each viewer enters in their own browser, or, with a capability FirstLine’s administrator enables, keep entries shared across everyone who opens it.

Good for
Checklists, sign-ups, small shared lists for staff.
Watch for
Not for student information.

The rule of thumb

  • FirstLine’s data stays in the warehouse. Read it where it lives; don’t keep copies that go stale.

  • Live records go where they can be edited: a Sheet for a team, a tool’s own database for anything bigger.

  • Trends go in BigQuery, kept in one shape year after year, so this year can be compared with last and one school with another.

Lessons we learnedfrom real FirstLine tools

Each happened to a real FirstLine tool.

  • Executing as you is the most common leak. An Apps Script web app set to Execute as Me shows every viewer whatever the script can read. Fine for a duty schedule. Not fine for a Sheet with student rows: execute as the user, or narrow Who has access to match.

  • Triggers die with their owner. An Apps Script trigger runs under the account that created it. When that person leaves, the Monday email stops and nobody is told. Create triggers from a team account, or hand them over before you go.

  • A green deploy is not a working app. Twice a deploy reported success while every page returned an error. The deploy now checks the app answers, and you still open the page and use it.

  • Tests live with the code. The first tool built from the starter kit had 68 tests that disappeared with the session that wrote them. Tests are committed with every change, and a red test blocks the merge.

  • One change at a time. Five changes in one afternoon on a live tool left a team unable to work. Ship one, check it, then the next.

  • Access by job title, never a list of emails. A list of emails is a lockout waiting for the next role change. Job titles from the staff roster move with the job, and must match it exactly: "Manager, HR" and "Manager HR" are different.

  • Every route that returns a person checks who is asking. Nine routes across five tools accepted ?email= and returned that person’s record to anyone. Check the caller, every time.

  • Made-up data isn’t made up until you check. Three of twelve invented student names in one prototype were real students. Check invented names against the roster before sharing anything.

  • A word can break a database. A history column named at, a reserved word in BigQuery, made every save fail. The starter kit now tests for it.

  • Ask the person who does the work. The Health Office tool was first built as though the nurse fills in the injury form. Her own words: the staff member on duty does, and she reviews it. Ask before you decide who the tool is for.

  • Grade codes are not grades. In FirstLine’s student data, grade -2 is the Discovery Program (fully self-contained special education), not pre-K 3. -1 is PK4 and 0 is K. Label them that way wherever a grade appears.
